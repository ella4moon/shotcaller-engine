# shotcaller-engine

An authoritative simultaneous-turn strategy engine with SQLite persistence and player-specific API views. It is a compact engineering demonstration: clients submit intentions; the server owns the clock, validates commands, resolves conflicts, and persists the result.

The demo deliberately restarts the server in the middle of a conflict. A private choice survives the restart, the missing choice times out, and the turn settles once.

## Run it

Requires **Node.js 24.14+**. No runtime dependencies, external services, credentials, or assets are needed for the demo.

```bash
git clone https://github.com/ella4moon/shotcaller-engine.git
cd shotcaller-engine
npm ci
npm test
npm run demo
```

The demo starts a loopback HTTP server, creates five authenticated seats, verifies hidden orders, creates a conflict, closes and reopens the server/database, and verifies recovery. It leaves an inspectable SQLite database in `data/demo/<run-id>/`. Its logical clock is injected internally; the public HTTP API cannot fast-forward time.

## What is implemented

- Pure, deterministic rules with seeded map income and immutable transitions.
- Simultaneous planning, sealed orders, connected conflict groups, secret votes, and deadlines.
- Missing orders become hold; missing conflict votes become withdraw.
- A late scheduler advances one overdue phase and opens a fresh decision window.
- SQLite transactions persist state, command receipts, and transition records together.
- Optimistic versions reject stale commands. Idempotency keys make retried commands safe.
- Random bearer tokens identify a specific seat in a specific match; only their hashes are stored.
- API responses use explicit allowlists. Opponents never receive private orders, treasury, or votes.
- An authenticated HTTP API, bounded requests, structured error codes, and graceful shutdown.

This is an engine and reference API, not the full private game. The public rules use a small fictional ring map and generic teams. Historical research, portraits, voice/TURN infrastructure, production credentials, users, and private operations are excluded.

## Start the API

Copy `.env.example` to `.env` and replace `ADMIN_TOKEN` with a random value generated by:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
npm start
```

The default listener is `http://127.0.0.1:3000`. Use the admin token only to create matches; distribute each returned seat token privately to that player. The creating administrator is trusted with all initial seat credentials. There is no account registration or matchmaking service in V1.

See [API examples](docs/api.md), [rules](docs/rules.md), and [architecture](docs/architecture.md).

## Operational boundaries

V1 supports a single authoritative Node process with a local SQLite database. It does not provide horizontal coordination, accounts, matchmaking, reconnect notifications, WebSockets, token rotation, archival, or a browser game UI. Clients can poll the view endpoint. Do not expose the reference API directly to the internet without a TLS reverse proxy and operator-specific access/rate-limit controls.

The database contains private orders and tokens' hashes. Keep its directory private and use a SQLite-consistent backup rather than copying only the main file while WAL writes are active. One database accepts up to 1,000 matches; there is no automatic pruning. JSON snapshots are authoritative; the transition table is an audit index, not a complete replay log.
